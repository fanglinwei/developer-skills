# Developer Skills

用于 Codex 的开发工作流工具包，提供代码审查、代码简化、项目检索、前端开发与界面复刻、功能文档和 Swift 编码规范。

## 安装与更新

```sh
codex plugin marketplace add fanglinwei/developer-skills --ref v0.1.5
codex plugin add developer-skills@developer-skills
```

从旧版本更新时，先移除旧 marketplace 来源，再执行上面的安装命令；已安装过同名来源时，直接添加不同 ref 会被 CLI 拒绝：

```sh
codex plugin marketplace remove developer-skills
codex plugin marketplace add fanglinwei/developer-skills --ref v0.1.5
codex plugin add developer-skills@developer-skills
```

安装后重启 Codex 或开启新聊天，从技能列表选择 `developer-skills` 下的对应 Skill。

当前发布版本：[v0.1.5](https://github.com/fanglinwei/developer-skills/releases/tag/v0.1.5)。本版更新 code-review 的证据分类、需求与规范核对、按需协作职责及独立复核规则，其余 7 个 Skill 保持不变。

## Skill 与用法

| Skill | 作用 | 调用示例 |
| --- | --- | --- |
| `code-review` | 按证据核实正确性、安全、需求与调用影响。支持 `daily`/`deep`，默认隐藏可选改进；获授权时按需分线与复核，只输出报告。 | `$developer-skills:code-review daily` 帮我审查当前改动。 |
| `code-simplifier` | 简化近期修改的代码，保持原有功能与行为，遵循项目规范。 | `$developer-skills:code-simplifier` 简化本次修改。 |
| `codegraph-project-scan` | 代码检索或读取前更新已有索引，同轮改动后重新同步；无索引或工具不可用时按项目规则回退。 | `$developer-skills:codegraph-project-scan` 查找订单提交入口及调用链。 |
| `frontend-ai-dev-docs` | 按功能梳理前后变化、交互、接口和影响范围，生成或持续维护模块迭代文档。 | `$developer-skills:frontend-ai-dev-docs` 总结订单模块本次功能变动，写入模块功能迭代总结。 |
| `frontend-page-clone` | 根据示例代码、网页或截图复刻页面或模块，复用项目组件，已有项目优先沿用原接口，缺口按需局部 mock。 | `$developer-skills:frontend-page-clone` 按这张截图复刻指定页面，采用原样复刻档位。 |
| `frontend-safe-development` | 约束浏览器 Web 前端开发，保持技术栈，检查相关状态、无障碍、安全和错误恢复。 | `$developer-skills:frontend-safe-development` 按项目现有方案修改这个表单。 |
| `frontend-style-clone` | 对齐局部布局、字体、颜色、控件和动画，保留现有业务数据、文案与交互。 | `$developer-skills:frontend-style-clone` 按参考图调整这个弹窗的外观。 |
| `swift-code-style` | 在 Swift 编写、重构及审查中应用命名、API、格式、安全解包与引用管理规范。 | `$developer-skills:swift-code-style` 按项目规范调整本次 Swift 改动。 |

调用示例中的页面、模块、参考图和改动范围需替换为实际目标，并提供相关材料。Skill 也可能按任务描述自动触发；需要明确选用时，从技能列表选择或显式输入名称。

## 代码审查

使用 `code-review` 检查代码正确性、安全、需求符合性和调用影响。你可以说“帮我 review 当前改动”，也可以指定文件、提交、分支或 PR。Codex 按任务选择模式，读取相关实现、调用方和测试，输出审查报告及最小修复建议。

完整规则见 [code-review Skill](skills/code-review/SKILL.md)。

### 功能特色

- **追踪行为与调用影响**：对照改动前后的返回值、异常、状态和副作用，检查调用方、配置及现有测试。涉及跨模块流程时，继续核对存储、迁移、重试和恢复。
- **核对需求与项目规范**：依据你提供的需求、验收标准和仓库规则，检查遗漏、部分实现、实现偏差及有实际影响的范围扩张。规范意见会注明规则出处；缺少规格时，审查者说明无法判断的部分。
- **先找反证，再确认缺陷**：审查者核实问题归因、触发路径、违反的约定和具体后果，并检查调用方限制、共享工具及框架或数据库防护。证据充分的静态调用链也可支持结论。
- **区分事实与未知项**：分别报告已确认缺陷、待确认和关键验证缺口。低优先级真实缺陷照常报告；你明确要求后，审查者才展开可选简化或优化建议。
- **给出可执行的建议**：每项缺陷附准确位置、触发场景、影响和最小修复方向。审查者合并同根因问题，并为逻辑修复提供能识别错误实现的验证场景。
- **按需协作**：你授权后，主审可分配需求、契约或边界检查，也可安排其他审查者复核关键发现。主审负责跨线核实、去重和最终报告。

### 选择 daily 或 deep

| 模式 | 适合的改动 | 审查重点 |
| --- | --- | --- |
| `daily` | 局部修复、单个功能、影响路径清晰的模块改动 | 范围内全部改动、相关调用方和被调用函数、有效测试 |
| `deep` | 跨模块流程、公共接口或共享模型、迁移，以及权限、资金、持久化、并发协议的跨模块影响 | 在 daily 基础上列影响清单，核对需求与实现、测试的对应关系，追踪输入到存储及输出，检查兼容性与失败恢复 |

你指定的模式优先。未指定时，审查者根据影响范围选择，并说明理由。选择 `daily` 后发现跨模块影响，审查者仍会核实，并在需要扩大范围时建议 `deep`。`deep` 的审查边界仍是你指定的目标。

### 调用示例

在 Codex 中从技能列表选择 `code-review`，或使用插件全名。以下提示词可按目标替换：

```text
帮我 review 当前改动。

$developer-skills:code-review daily 审查 src/orders/ 的当前改动及调用影响。

$developer-skills:code-review deep 以 main 为基准审查当前分支，需求和验收标准见 docs/spec.md。

$developer-skills:code-review daily 审查提交 <commit>。

$developer-skills:code-review deep 审查 PR <URL>，重点检查权限与数据写入。

$developer-skills:code-review daily 检查这个 Web 页面改动，附上可选简化建议。
```

自然语言要求“检查这段代码有没有问题”或工作流进入实际代码审查时，也会触发本 Skill。普通代码解释、Skill 分析和改造计划讨论不触发审查。PR 内容及关联材料需通过当前可用且获准使用的工具读取。

### 范围与准备材料

| 你提供的目标 | 审查者如何处理 |
| --- | --- |
| 未指定目标 | 合并检查当前已暂存与未暂存改动，纳入相关的未跟踪源码、配置和测试，排除生成物、第三方目录及敏感文件 |
| 文件或代码片段 | 审查指定实现，读取判断影响所需的关联代码；无需先制造 diff |
| 提交 | 使用 `git show COMMIT` 查看目标提交 |
| 分支 | 通常使用 `git diff BASE...TARGET`；你要求直接比较两个版本时使用 `git diff BASE TARGET` |
| PR | 确认基准与目标版本，结合可读取的 PR 说明和关联需求审查 |

审查当前改动时，如果工作区没有改动，审查者会说明“当前没有可审查的改动”并停止。需要审查最近提交时，请指定该提交。

提供目标范围、比较基准和相关需求即可开始；涉及项目规范时，附上对应文件路径。缺少规格时，审查者继续检查可确认的调用约定与行为。缺少会改变结论的事实时，审查者列明缺什么、如何取证，以及取证结果如何影响判断。审查期间代码变化后，审查者会重核受影响的证据和行号。

### 报告内容

报告开头说明行为变化、范围、模式、目标版本及必要假设，省略空分组。

| 分类 | 你会看到的内容 |
| --- | --- |
| 已确认缺陷 | 按高、中、低排序；列出文件位置、触发场景、实际与预期行为、约定依据、问题归因、证据、影响和最小修复 |
| 待确认 | 有具体源码路径和依据，但缺决定性事实；列出最小取证方式及不同结果对应的判断 |
| 关键验证缺口 | 指明关键行为、可能漏检的错误实现、现有检查缺什么及建议验证；仅缺测试文件或覆盖率不足不构成此项 |
| 可选改进 | 你明确要求后，列出有具体收益的简化、维护性或优化建议 |

已确认缺陷按实际后果、影响范围和触发条件分级。高优先级包括已证实的越权、重要数据损失或关键主流程失效；中优先级影响部分用户或重要分支；低优先级覆盖影响较小的真实错误。待确认项和验证缺口不计入缺陷分级。

报告结尾给出合入建议、实际验证及限制。有高优先级缺陷时先修复；关键路径未审查、待确认项或验证缺口阻碍判断时，结论为“暂无法判断是否可合入”。未发现已确认缺陷时，审查者写明“未发现可确认的缺陷”，并限定已审查范围。报告会区分静态分析、已运行检查和建议验证。

### 依赖与执行边界

- 所有审查都需要已安装的 `ponytail-review`。非浏览器 Web 前端审查按需结合 `karpathy-guidelines`。
- 浏览器 Web 前端审查在两种模式下都结合 `frontend-safe-development` 和 `karpathy-guidelines`，检查语义与键盘操作、响应式布局、状态、异步错误恢复、客户端安全及性能。此组合适用于混合项目中的浏览器 Web 部分。
- 审查者会核对实际加载的 Skill 与依赖路径。缺少依赖时，停止依赖它的部分，继续其他独立检查，并披露未覆盖范围；工具包不代为安装依赖。
- 审查者只输出报告和建议。修改代码、测试、配置、格式，以及 Git 写操作，需要另行授权。
- 审查者可以运行相关的现有最小检查，前提是不会改写源码、快照、锁文件或业务数据，也不访问生产系统或执行外部写入。有疑似副作用时，采用静态证据并说明限制。审查期间不安装或升级依赖、不新建测试文件、不启动长期服务。

### 授权子代理协作

`daily` 和 `deep` 默认都由主审完成。需要协作时，你可以这样指定范围与预算：

```text
$developer-skills:code-review deep 以 main 为基准审查当前分支。
允许子代理协作，最多调用 3 次，预留一次复核关键发现。
需求见 docs/spec.md，重点检查订单状态与失败恢复。
```

主审在授权范围内判断是否值得委派。`deep` 获授权且适合协作时，默认总调用上限为 3 次；你指定的上限优先。分线、复核、重新委派及升级或备用接续都计入预算，实际并发还受宿主容量和适用的 agent-fit 规则限制。

主审按需选择四类职责：A 核对需求，B 追踪契约与调用，C 检查权限、持久化等边界，D 独立复核候选发现。职责可以合并；复核者须未参与提出该候选。主审负责未委派部分及整体覆盖，多人同意也需源码或验证证据支持。必需复核无法完成时，主审会披露阻塞。

交接要求和职责模板见[代理协作协议](skills/code-review/references/agent-collaboration.md)。

## 页面复刻与局部样式调整

- **完整页面或模块复刻**：使用 `frontend-page-clone`。可选择保留项目组件风格，或尽可能按参考原样复刻；已有项目保留原接口与业务行为，仅对明确缺口使用局部 mock；无接口的纯演示项目默认使用 mock。
- **现有页面的局部视觉调整**：使用 `frontend-style-clone`。调整指定区域外观，保留正式业务逻辑、数据、绑定和文案。

## 按场景使用的依赖

- 代码审查需要 [Ponytail](https://github.com/DietrichGebert/ponytail) 的 `ponytail-review`；界面复刻的实现阶段使用其 `ponytail`。
- 复刻存在关键未决选择时，使用 [Matt Pocock Skills](https://github.com/mattpocock/skills) 的 `grilling`。
- 开发和审查按适用规则使用已安装的 `karpathy-guidelines`。
- CodeGraph 检索需要对应 CLI；网页分析和视觉验证需要可用且获准使用的浏览器工具。

工具包不会自动安装外部依赖。实际执行遵循用户指令、项目规则及各 Skill 的权限边界；缺少依赖时，说明受影响的步骤和未完成范围。

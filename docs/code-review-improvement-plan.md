## 去重后的改进清单

### 1. 统一需求和规范依据

- 在 description 中明确实际代码审查的触发范围；单纯解释审查机制、分析 Skill 或评审其改造计划，不因包含 review 一词启动代码审查。正文与元数据采用一致边界，触发验证见第 11.5 项。
- 优先使用用户明确指定的当前需求与验收标准，并遵守适用指令和项目规则。
- 未指定时读取直接关联的本地规格、任务说明及已有上下文；有明确关联的 issue/PR 时，按工具能力及现有读取权限获取。
- 核实来源的适用版本、范围和权威性。来源冲突或过时时说明；仅在会改变具体结论时询问必要信息。
- 有需求时检查遗漏、部分实现、实现错误和有实际影响的范围扩张；必要校验、错误处理或兼容逻辑不因规格未逐项提及而自动成为越界。
- daily 核对直接相关要求；deep 建立简短的需求—实现—测试对应关系。没有规格时继续可独立完成的审查，限制需求符合性结论。
- 规范类发现引用具体规则与位置。区分规范不符与行为缺陷；只有同时满足第 2 项门槛，才称为已确认缺陷。其余按实际维护影响和 Q1 处理。项目规范优先于通用设计启发式。

验收：需求原文与推测用途不混淆；旧 issue 不覆盖明确的当前要求；合理配套实现不被误报为范围扩张。

### 2. 合并正式缺陷准入与变更归因

每个候选在进入已确认缺陷前，核实：

1. 与审查目标相关：本次引入、加剧或使问题首次可达，并说明具体改动及前后行为。指定文件或片段审查按其目标判断，不虚构不存在的 diff。
2. 当前调用方、输入或状态能触发。
3. 违反可确认的需求、接口约定、安全边界或既定行为。
4. 已核实的上下游、框架、数据库等保护无法阻止结果。
5. 存在具体错误后果及受影响对象。

充分静态证据可以确认问题；不强制动态复现。位置可以在改动行之外，但必须说明与本次改动的因果关系。保留现有例外：直接阻碍当前改动安全使用的既有问题可单列，明确其来源，不归因为本次引入。

验收：缺少决定性证据的候选不进入缺陷清单；不把改动附近的既有问题归因于本次改动。

### 3. 主动反证与证据状态

报告前主动寻找能够推翻候选的调用方约束、框架保证、数据库约束、现有测试、需求允许行为和运行前提；发现有效反证后撤销或修正。

- 已确认：通过第 2 项准入。
- 待确认：有具体源码路径及成立依据，但缺少决定性事实；列出最小取证方式，以及不同结果如何改变判断。
- 已排除：有效防护、预期行为、不可达条件或无实际后果推翻候选，默认不进入报告。

无具体路径或可检验主张的猜测不进入待确认。现有测试是证据之一，不以“测试通过”代替源码判断。严重的潜在后果不能替代成立证据，不使用未经校准的数字置信阈值。

验收：能撤销被保护的假阳性；未知部署条件不会被猜测补齐；多个代理同意不作为真实性证据。

### 4. 分离关键验证缺口

执行已确认 Q2 和 Q5。报告应说明未验证行为、可能漏检的具体错误实现，以及能区分正确与错误实现的验证场景；检查现有测试是否已提供等效验证。

单纯新增分支、没有测试文件或覆盖率数字不足，不直接构成缺陷或关键验证缺口。源码已证明错误时报告缺陷并附必要回归场景，避免把同一事实重复列为验证缺口。审查期间不为此新建测试文件。

验收：实现错误与验证不足清楚分开；泛泛的补测试建议被过滤，实际阻碍判断的缺口被保留。

### 5. 重写优先级并收紧性能、复杂度判断

按已确认 Q4，先确认成立，再根据后果、范围和触发条件分高/中/低。功能错误、兼容性变化等类别名称不直接决定高优先级；已确认低优先级缺陷仍报告，不与默认隐藏的可选改进混淆。待确认项和关键验证缺口不沿用缺陷等级，但可以明确阻碍合入判断。

性能判断需有依据的数据量、频率、并发或部署条件，并解释成本与用户影响；循环、复杂度符号和 N+1 形态只是调查线索。复杂度建议需说明具体理解、维护或一致性负担，沿用最小完整修复原则和已知 shortcut 限制。

验收：局部轻微错误与主流程数据损失获得不同优先级；无实际负载依据的性能担忧及纯设计偏好不成为缺陷。

### 6. 按需分线与职责契约

仅在有委派授权、收益明确且宿主能力可用时启用；主审先了解改动再划线。缺材料不通过增加代理解决。高度耦合的任务可以由主审集中检查，按需使用独立复核。

按改动选择最少必要职责，采用下述固定模板；规范与证据标准为共同要求，不固定为独立代理。角色以调查方法定义，不采用严厉、宽松等诱导结论的性格，也不设发现数量指标。

#### 6.1 公共任务契约

所有职责复用同一契约，每次填入实际材料，公共质量规则只引用主 Skill 中的权威定义，不在四份模板各复制一遍。

| 字段 | 交接要求 |
| --- | --- |
| 目标与版本 | 模式、目标、比较基准、精确 diff、适用提交列表；区分索引、未暂存与相关未跟踪文件。 |
| 职责与范围 | 选用模板及所负责入口、模块或判断维度；必要关联读取范围与排除范围。 |
| 权威依据 | 当前需求、验收、适用规范、接口约定和适用 Skill 的实际路径或必要正文。 |
| 必要事实 | 已核实的源码、权限及配置事实、假设和缺失材料；首轮不交接主审预判或其他线未核实结论。 |
| 协作边界 | 其他线负责内容、共享接口与跨线流程负责人；范围限制责任，不禁止必要关联阅读。 |
| 验证限制 | 只读权限、允许的现有最小检查、工具/时间限制及适用调用预算。 |
| 完成要求 | 本任务应覆盖的路径、停止条件、专项返回及未完成部分的披露方式。 |

共同执行要求引用第 2–5、8、10 项及主 Skill：根据指定版本和依据调查，主动反证，按同一门槛分类；材料变化时重核，返回真实覆盖和限制，默认工具返回、不写共享报告、不递归委派。主审保留跨线核实、冲突处理、根因去重及最终合入判断。

#### 6.2 四份短职责模板

各模板固定目标、检查方法、完成条件与专项返回；每次仅填本次范围及材料，不固定代理身份、数量或模型。

| 模板 | 固定检查方法 | 完成条件 | 专项返回 |
| --- | --- | --- | --- |
| A：需求核对 | 将分配范围内的要求对应到实现和现有验证；检查遗漏、部分实现、实现偏差和有实际影响的范围扩张；核实需求版本与冲突。必要校验、错误处理和兼容工作不因未逐项列出而自动越界。 | 每条分配范围内的明确要求都有判断；缺失或冲突依据限制结论，不自动扩展整份规格。 | 需求位置 → 实现位置 → 符合性判断 → 证据或决定性缺失事实。 |
| B：契约追踪 | 追踪入口、相关调用方与必要下游；核对参数、返回值、异常、副作用、异步时序；按改动深入旧调用方、默认值、格式、混合版本及失败/重试/取消/恢复路径，核实实际保护。 | 受影响契约和关键调用路径均有判断；未追踪部分明确列出。 | 变化的契约 → 可达调用路径 → 实际结果 → 受影响调用方。 |
| C：边界检查 | 明确主体、已有能力、输入及受保护资源；定位授权、隔离、一致性或资源控制，追踪敏感操作和替代入口；按变化检查批量、并发、存储写入、迁移、重试和恢复及已有保护。缺最佳实践不自动是漏洞；决定性外部事实未知则待确认。 | 指定边界的关键路径和防护有判断，阻碍判断的事实缺口明确；不自动扩展为整库渗透测试。 | 主体与能力 → 控制点 → 路径 → 受影响资源及具体结果。 |
| D：独立复核 | 前提为已获授权且未参与提出该候选；从当前源码重建路径，尝试推翻可达性、约定违反、防护无效和影响主张，检查最小修复必要性及相关路径完整性。输入包括候选及必要证据，不含其他复核者结论。 | 关键前提与影响都有有据判断，无法确定的事实精确列出；该过程不称完全盲审。 | 成立／部分成立／不成立／缺少证据，以及依据、修正意见或缺失事实。 |

存储、迁移与失败恢复没有被删除或遗忘：调用/版本/时序契约归 B，授权、隔离和持久化一致性约束归 C；主审在公共契约中明确具体归属与交叉点，必要时将同一模板按子系统拆分，或由同一审查者承担 B+C。无需为此默认增加第五份模板。

#### 6.3 统一返回与动态选择

共同返回结构为：职责与目标版本 → 实际覆盖及依据 → 已确认发现 → 待确认 → 关键验证缺口 → 实际验证与未完成部分。发现沿用主 Skill 的位置、场景、证据、影响和最小修复格式；空栏省略，可选改进仅按 Q1 展开。专项返回作为共同结构中的证据或覆盖摘要，不再另写一份重复报告。D 使用专项判定，由主审映射证据状态，不强迫复核者产生新缺陷清单。

职责可由主审承担，也可在授权后交给子代理；一人可承担多个职责，候选提出者不得兼任该候选的独立复核者。小修复可由主审用 B 完成；明确规格的跨模块功能可选 A+B；权限或数据变更按需选 C；争议候选再用 D。四份模板不要求每次全部启用，也不等于四次调用；实际委派继续遵守第 7 项的总预算和复核预留。

| 职责 | 启用条件 | 停止或降级条件 |
| --- | --- | --- |
| A | 存在可引用的需求或验收依据。 | 依据缺失或冲突时限制相应符合性结论并列明缺口，不补造需求；不为缺少依据单独派发 A，其余审查继续。 |
| B | 改动影响参数、返回值、异常、副作用或状态转换。 | 分配范围内受影响契约与关键路径完成检查后返回；无法读取或追踪的路径披露为未完成。 |
| C | 改动触及权限、隔离、持久化、一致性或资源控制。 | 关键路径和防护有据判断后返回；决定性部署或运行事实缺失时停止相应断言，说明需补充的证据，其余路径继续。 |
| D | 存在值得复核的候选，已获授权、有剩余预算且有未参与提出该候选的执行者。 | 形成有据的确认、部分成立、反驳或证据不足结论后返回；缺前提时报告限制，不将原作者自查替代为独立复核。 |

未委派的维度仍由主审负责。主审根据改动核查整体覆盖，包括性能、资源释放、错误恢复及其他适用维度，不把 A–D 的角色名称当作完整检查清单。某个角色完成只证明其分配范围的进度，不能据此宣布整次审查完成；交付前对照目标与实际覆盖核实缺口。跨线事实保留源码或配置来源，其他执行者仍可重新核实，不将主审已核实标签作为免检结论。

#### 6.4 计划中的文件组织

公共契约、A–D 四份短模板、统一返回与启停规则已统一写入 `references/agent-collaboration.md`，替换原简略职责表。协议目前 95 行，无需新增 `references/review-roles.md`；主文件在协作分支明确指向，子代理须能读取所选模板，否则主审提供必要正文，不只给角色名。未来确有长度负担时再拆分。

未为职责新增 Skill、注册系统或配置层。授权、模型、effort、预算、证据门槛与隔离规则继续引用现有权威位置。

验收：不同执行者拿到同一模板后，均知道检查什么、何时完成及按何种证据门槛返回；每条线职责明确且信息充分，共享接口和跨线流程有负责人，不因划线丢失存储/恢复路径或重复报告。本轮完成 7 个独立上下文协议决策练习，不能将其或结构检查视为真实分线与故障场景验收。

### 7. 代理预算与路由

按已确认 Q7 控制总调用数，同时限制并发。上限不是使用配额，预计需要复核时预留额度。实际执行服从用户限制、宿主空闲容量和 agent-fit；重试、升级与备用不得绕过任一适用上限。

达到上限后主审继续可独立处理的工作；无法完成的必需复核或覆盖如实报告，既不静默追加，也不将自身检查称为独立复核。模型、effort 及故障处理沿用 agent-fit，不在专业 Skill 中重复定义。

验收：累计与并发数量均可解释；不串行创建代理绕过预算；实际能力不足不会被报告成完整成功。

### 8. 隔离判断上下文并固定审查版本

需要独立判断且宿主支持时，优先不继承父会话历史，由主审完整交接。首轮不传递主审预判、其他代理未核实发现或置信度；共享目标版本、标准和必要事实。经核实且影响其他线的事实由主审同步。

独立上下文不等于缺少上下文，需求、权限模型、接口契约及必要源码都应可用。所有发现绑定明确版本；包含未提交改动时区分索引与工作区。审查期间目标变化需重新核对受影响证据，不自动创建快照提交。

子代理默认通过工具返回结果，主审独占最终报告和共享状态；不读取其他审查者草稿。必要临时输出分目录隔离，继续遵守只读审查和检查副作用限制。历史隔离及独立目录均不宣称提供操作系统级权限隔离。

验收：子代理不继承无关预判；也不因缺少事实而猜测；不同版本结论不混用，文件隔离能力表述准确。

### 9. 关键发现独立复核

按已确认 Q3，为高影响、争议大或容易误报的候选按需安排未参与发现的复核者。分线审查本身不算对某项发现的独立验证。

复核者接收候选主张、位置、触发条件、必要证据和适用规则，不接收其他复核者结论；从当前源码尝试推翻可达性、防护无效或影响主张。返回成立、部分成立、不成立或缺少证据，以及依据和修正意见。主审据此映射到第 3 项证据状态。

验收：能否定主审错误主张；接受候选供复核不称为盲审；不把当前审查者自查描述为独立复核。

### 10. 统一报告、根因去重与覆盖说明

按 Q1、Q2 调整默认报告：已确认缺陷按处理优先级呈现，单列阻碍判断的待确认项和关键验证缺口，说明实际验证、覆盖限制和合入判断；可选改进仅按需展开。

需求与规范分别检查，最终合并整合。同一根因只报告一次，保留不同影响、状态写入及恢复分支。规范不符、行为缺陷及维护建议准确命名，不用一类事实冒充另一类。不设固定问题条数上限。

daily 简短说明范围；deep 或协作增加审查线与覆盖情况。冲突由主审核实，无法裁决的保留待确认；子代理完成声明不替代覆盖证据。已排除候选默认不输出。合入结论与已确认问题、关键未知项及覆盖情况一致。

验收：报告集中但不隐藏真实低优先级缺陷；不重复呈现测试建议或根因；关键路径未审查时不作无保留合入建议。

### 11. 固定样例与对照评测

按已确认 Q6 冻结材料、预期判定与执行条件，比较改造前后结果；逐例检查真实性、归因、优先级、分类、去重、覆盖和成本。先验证规则，再检查协作是否有额外收益；不以报告变短、发现更多或代理更多作为成功依据。

#### 11.1 分开发现能力与候选判别

现有 24 个场景保留为判断、分类与反证回归集；其中候选和决定性理由已给定，人工推演只能检验规则可解释性，不能证明实际发现能力。判别运行可提供候选主张，预期分类和决定性理由仍只供评分。

另先建立 2–3 个固定、可执行的最小仓库与真实任务提示：

| 发现任务 | 审查者输入 | 检验目标 |
| --- | --- | --- |
| 含有效保护条件的改动 | 完整的最小源码、diff 与必要需求。 | 自行读到上下游防护，避免误报。 |
| 含跨调用链真实缺陷的改动 | 固定仓库、diff 与正常项目规则。 | 不靠候选提示发现缺陷，追踪可达性和实际影响。 |
| 需求只实现一部分的改动 | 固定仓库、diff 与明确需求。 | 发现遗漏，同时保留必要配套实现。 |

提示采用真实用户表达，不点出缺陷位置或预期结论。发现运行只提供仓库、改动及必要依据，不提供候选、预期分类或决定性解释；不得让执行者自行补出缺失源码。标准答案、评分和其他运行输出放在执行者不可访问的评分侧；同目录下仅靠提示要求不读取不算答案隔离。达不到访问隔离时披露限制，不把该轮标为干净发现评测。

#### 11.2 分阶段对比与完整冻结

| 阶段 | 对比 | 回答的问题 |
| --- | --- | --- |
| 规则 | 旧版 Skill 与当前规则版；采用相同的不委派执行条件。 | 准入、反证和分类是否改善结果？ |
| 模板 | 当前规则版与加入固定职责模板的版本；保持相同执行者安排和调用预算。 | 职责契约是否减少漏查、交接缺失和重复判断？ |
| 协作 | 同一模板版本的单代理与多代理；其余输入和适用规则一致，记录实际资源差异。 | 委派收益是否足以覆盖启动、交接、汇总、复核和返工成本？ |

顺序推进，每轮只检验对应变化；不一次改变规则、模板、模型组合及代理数量后归因。正式比较前保存可恢复的完整 Skill 版本及实际加载的参考文件、依赖 Skill、项目规则和版本或哈希；当前 0.1.4 主文件仅是文本基线，不代表完整运行基线已冻结。旧依赖无法取得或无法证明等价时限制该对比的结论，不以当前依赖冒充旧版环境。

同一对比使用相同模型/effort、工具能力与必要权限，保存可信运行元数据及 agent-fit 完整任务快照（如委派）；不同版本使用干净上下文，避免同时加载另一个版本或旧预期答案。按第 7 项核算每次实际审查的预算，不以评测为由绕过授权、次数或容量。随机化或互换执行顺序，必要时有限重复，说明差异与波动。

#### 11.3 可核对验收与评分纠错

验收同时读取输出与实际执行记录；标题齐全、报告变短、声称已检查或只报告零问题均不构成通过证据。

| 类别 | 判据 |
| --- | --- |
| 硬约束 | 无虚构检查或证据、无越权修改、无超预算委派；版本变化、工具失败、未知退出状态、截断与未完成范围如实披露。依实际工具与调用记录核对，违反时该轮不通过。 |
| 发现与真实性 | 逐项核对固定任务的已知真实缺陷是否发现、无效发现是否被过滤、源码路径及变更因果是否成立；不把关键缺陷漏报或错误降为待确认当作降噪收益。 |
| 分类与整合 | 证据状态、严重程度或合理范围、关键验证缺口区分正确；同根因不重复且关键影响路径不丢失。 |
| 成本与可用性 | 记录可观察的端到端耗时、调用及 token 等指标，检查必要证据与行动建议是否清晰；缺失指标标未知，不按模型名估算实际账单。 |

首轮在运行前固定每例必需发现、可接受判定和硬约束；所有必需项有证据通过后才声明该组验收通过，不将均分掩盖关键失败。不预设未经测量的提升百分比；没有辨别力的判据、结果波动与质量/成本取舍单独分析，不只报告总通过率。

标准答案可纠错：新发现超出答案但有证据时人工裁定；有效反证推翻答案时修订预期，保留理由和版本，并按修订后同一口径重评相关对照。第一轮调整后，用未参与规则改写的少量保留任务验收；答案一旦用于调优，后续不再称该任务为未见验收集。

#### 11.4 场景覆盖

| 样例组 | 必须包含的情形 |
| --- | --- |
| 假阳性与状态 | 上游已保护、框架/数据库保证、需求允许行为、不可达路径、未知部署前提、无具体证据猜测。 |
| 归因与真实性 | 无关既有问题、被改动首次暴露的问题、真实越权、数据损失、兼容性及并发缺陷。 |
| 需求与规范 | 明确需求遗漏、部分实现、实现错误、合理配套改动、真实范围扩张、当前要求与旧 issue 冲突、缺少规格、规范与启发式冲突。 |
| 验证与优先级 | 仅缺测试、已有等效测试、关键失败恢复缺口、轻微功能错误、默认路径严重后果、低负载下的性能担忧。 |
| 整合与覆盖 | 同根因多路径、恢复分支遗漏、代理报告冲突、部分范围未完成、工作区中途变化。 |
| 协作约束 | 无授权、预算不足、上下文交接缺事实、未传递主审预判、独立复核推翻候选。 |
| 职责模板增补 | A 缺需求时限制结论；B 可阅读必要需求和下游；C 覆盖存储/迁移/恢复的一致性；主审承担或同一人兼任职责不自动增加调用；D 拒绝由候选提出者兼任；四模板按需选择且预算 3 时不自动启动四代理；专项返回不重复生成报告。部分决策已演练，实际协作待验收。 |
| 整体责任与停止 | 未委派维度由主审承担；角色完成不等于全局完成；外部事实缺失限制相应断言；关键路径未读不得报告覆盖完整。决策已演练，实际调度待验收。 |

记录遗漏真实缺陷、无效发现、重复报告、错误分类、规则未执行，以及可观察的时间与调用开销；没有对照测量不宣称提速。能力不足的项目标未执行，不推测结果。

#### 11.5 触发边界、异常与目标宿主

元数据调整后，在目标宿主中验证真实任务表达及近似但不应触发的请求：

| 请求或运行情形 | 预期 |
| --- | --- |
| “检查当前分支的改动有没有问题”“审查这个 PR 的权限改动” | 触发实际代码审查，按任务选择范围。 |
| “解释 code-review Skill 的工作方式”“使用 skill-creator review 这份 Skill 改造计划” | 执行解释或方案评审，不启动实际代码审查流程。 |
| 必要依赖不可用、当前目标没有可审查改动 | 准确报告受影响范围或无可审查内容，不补造检查与发现。 |
| 子代理超时、返回截断或工具失败 | 披露未完成范围，遵守剩余预算和故障规则，不以部分输出替代完整成功。 |

可复用 skill-creator 的评测与评分方法；依赖 Claude CLI 的触发优化脚本不直接代表 Codex 的实际触发效果。先核对目标宿主的工具、上下文隔离、模型元数据、委派与记录能力；不兼容时保留缺口，采用宿主可验证的方法，不为适配新建一套运行框架或伪造指标。

#### 11.6 人类反馈与迭代闭环

每轮按迭代保存实际输入、版本、输出、评分、必要执行记录、可获取成本与反馈，和评分侧答案分开管理。使用 skill-creator 自带的 `eval-viewer/generate_review.py` 展示输出与指标；无浏览器服务时使用静态导出，先核对现有数据与查看器 schema 的兼容性，不另建反馈系统。

用户集中评审问题有效性、遗漏、证据充分性、建议可执行性、报告可读性及覆盖限制；反馈保存到该轮 `feedback.json` 或明确记录的等效材料。没有反馈时保留待评审状态，不将沉默当作认可。读取反馈后只调整有依据的共同规则，在新迭代中用相同口径复评并检查保留任务，避免逐例硬编码。

用户认可且验收通过，或已无可证明的有效改进时停止迭代；后者如实保留未满足项。没有体现收益或存在明显退化时保留上一稳定版本，不以文案或结构检查通过替代真实效果结论。

## 端到端流程

1. 确定目标、比较方式、适用规则和当前版本，选择 daily/deep。
2. 找到需求与规范依据，明确冲突、假设和无法判断的部分。
3. 对照前后行为，建立必要影响范围；获授权且有收益时按预算分线。
4. 阅读关联路径，按准入条件识别候选，并运行允许的最小现有检查。
5. 主动反证，区分证据状态、关键验证缺口与可选改进。
6. 按需独立复核；主审检查跨线契约、版本一致性及冲突。
7. 根因去重、确定缺陷优先级，按实际覆盖和证据统一交付。

## 实施与交付

1. Q1–Q7 已全部确认，按上述标准实施，不重复询问。
2. 已读取实际源码、已有修改及相关脚本，确认改动前源码与 0.1.4 缓存一致；保留已有计划和术语材料。
3. 先更新分类、准入、依据和报告，再补协作、隔离及复核。共同规则只有一处权威定义，daily/deep 和代理交接引用它，不重复整段。
4. 先按第 11.1–11.3 项补齐最小真实发现任务、完整冻结材料和可核对验收，执行具备前提且获授权的规则对比；缺前提的部分保留 PARTIAL，独立可完成的模板设计继续推进。
5. 模板增补按第 6 项落地公共契约、A–D 模板、启用与停止规则及统一返回，再按第 11.2 项分别验证模板和协作。代理材料按需加载，确有长度负担才拆参考文件；术语表不复制执行流程。
6. 调整 description 与正文的触发边界，补触发、异常和目标宿主验证；按第 11.6 项展示实际输出、收集反馈并迭代。无执行能力的项目明确保留限制。
7. 交付更新的 Skill、必要说明与术语、样例及结果。本次计划更新不包含安装、暂存、提交、推送或发布。

## 暂不纳入

- 固定代理阵容、新增第三种审查模式、角色配置系统或硬编码模型。采用第 6 项的固定职责模板和动态选择作为替代；模板不规定每次的代理阵容。
- 数字置信度阈值、发现数量指标、完整 Fowler 清单或强制建议重构。
- Cloudflare 式六阶段整库审计、持久化机器账本及独立沙箱编排。
- 自动修复、补测试文件、发布 PR 评论及其他外部写入。
- 在计划或规则中承诺未经测量的降噪比例、完整覆盖或加速效果。

## 风险与验收原则

准入过严可能漏报；过滤要同时验证真实缺陷保留。分线可能丢失交叉影响；主审保留整体责任。隔离可能丢失事实；交接必须完整。优先级与报告分类变化可能引入歧义；保持缺陷、待确认、验证缺口和可选改进分离。规则过长可能降低执行稳定性；按共同流程与按需参考组织，去除重复。

只有规则、样例和实际结果相符，且未完成部分被准确披露时才声明相应改进完成。提示词不提供宿主级权限隔离，多代理一致不证明事实成立。
